STEP 2 — ADMIN ANALYTICS DASHBOARD + GRAPHS
Step 1 is complete. The project now has persistent first-party analytics for visitors, sessions, app opens, screen views, anonymous IDs, verified signed-in user IDs, platform, app version/build, Dubai-time reporting support, and database-backed deduplication.
For Step 2, build a proper Admin Analytics Dashboard using the Step 1 tracking foundation.
Do not redesign the tracking architecture unless something is genuinely broken. Do not change payment logic, transaction logic, authentication, marketplace behaviour, or unrelated Admin pages.
Before implementation, inspect the exact Step 1 schema, event names, API routes, session logic, and existing Admin Stats code and use those real names rather than creating duplicate analytics systems.
1. Main objective
The Admin Stats area should let me quickly answer:
- How many people are opening Saman?
- How many unique visitors are using it?
- How many signed-in users are active?
- How many sessions are happening?
- Are users new or returning?
- Is usage increasing or decreasing?
- Are users mainly on iOS, Android, or Web?
- Which app versions are active?
- Which screens are being used most?
- How does the current period compare with the previous period?
- What is happening with revenue?
This step should focus heavily on graphs, trends, comparisons, KPIs and reporting.
2. Admin Stats navigation
Upgrade the existing Admin Stats area with these tabs:
Overview | Users | App Activity | Screens | Revenue
Do not add acquisition attribution, search analytics, seller-contact analytics, listing conversion funnels, or advanced retention cohorts yet.

Add one consistent date filter at the top of Stats:

- Custom Range

00:00 Asia/Dubai through now

4. Overview KPI cards
Show these primary KPI cards:
- App Opens
- Sessions
- Unique Visitors
- Signed-in Users
- New Visitors
- Returning Visitors
- Screen Views
- Sessions per Visitor
Definitions:
App Opens
= actual Step 1 app_open events.
Do not use old login_events visits as App Opens.
Sessions
= Step 1 analytics sessions.
Unique Visitors
= distinct persistent anonymousId values active during the period.
Tooltip:
“Unique browser/device analytics identities. One person using multiple devices may count more than once.”
Signed-in Users
= distinct verified user IDs seen in analytics.
New Visitors
= visitors whose firstSeenAt falls within the selected period.
Returning Visitors
= visitors active during the period whose firstSeenAt predates the selected period.
Sessions per Visitor
= sessions / unique visitors.
Handle zero denominators safely.
5. Previous-period comparisons
Every major KPI should show the change compared with the immediately preceding equivalent period.
Examples:
Today → previous Dubai calendar day
Last 7 Days → previous 7 days
Last 30 Days → previous 30 days
Custom 10-day period → previous 10 days
Show values such as:
+14.2%
or
-8.4%
If the previous period value is zero, do not show a misleading infinite percentage.
Show a sensible label such as:
New activity
or simply show the current value without a percentage.

Hovering or tapping a point should show:

8. DAU, WAU and MAU
Add:
DAU
= distinct anonymous visitor identities active during the relevant Dubai calendar day.
WAU
= distinct anonymous visitors active during the trailing 7 days.
MAU
= distinct anonymous visitors active during the trailing 30 days.
Add:
DAU / MAU Stickiness
Formula:
DAU / MAU × 100
Include a trend graph for DAU / WAU / MAU where appropriate.
Include a tooltip explaining that visitor identities are device/browser identities and are not guaranteed to represent unique physical people across multiple devices.

17. Server-side aggregation
Do not fetch all raw analytics events into the browser and calculate charts client-side.
Aggregations must happen in PostgreSQL/server-side queries.
Create clean Admin reporting endpoints for chart-ready data.
For example, conceptually:
/api/admin/analytics/overview
/api/admin/analytics/timeseries
/api/admin/analytics/platforms
/api/admin/analytics/screens
/api/admin/analytics/versions
These are examples only. Reuse or extend existing Step 1 endpoints if that architecture is cleaner.
Time-series endpoints should support parameters such as:
- start date
- end date
- interval
- metric
- platform where applicable
Design this assuming analytics_events may eventually contain millions of records.
Use the indexes created during Step 1.
Avoid N+1 queries.
18. Historical data

“Detailed analytics collection began on [date]. Earlier activity is unavailable for these metrics.”
Do not silently merge old login_events into the new App Opens metric.
Existing genuine historical revenue and signup data may continue to use their original authoritative sources.
19. Existing heartbeat

- Sessions

20. Admin security
Every analytics reporting endpoint must require verified Admin authorization on the server.
Do not rely only on hiding the Admin UI.
Do not trust a raw client-provided user ID for authorization.
21. Performance
The analytics dashboard must not negatively affect normal marketplace performance.
Use:
- indexed queries
- server-side aggregation
- reasonable result sizes
- pagination for raw/recent-event tables
- efficient grouping
Do not return thousands of raw events just to draw a graph.

Do not redesign unrelated Admin sections.
23. Metric consistency

App Open
= actual tracked foreground/open event.
Session

Unique Visitor

Returning Visitor
